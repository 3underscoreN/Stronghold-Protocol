### 37.1 LLM latency and JSON recovery (round54, in development)

维护者问题：「思考强度降低一些出结果速度是不是就能跟上对局了」。本轮只修改开发用适配器；
发布门禁 `server/match/llmRelease.js` 和打包排除列表不变。没有调整游戏规则、时间预算、默认
模型／强度、普通 bot 或生成数据；不将小样本速度提升解释成终极胜率提升。

来源：[DeepSeek 思考模式](https://api-docs.deepseek.com/guides/thinking_mode/)、
[Chat Completions API](https://api-docs.deepseek.com/api/create-chat-completion/)，核对于 2026-10-26；
实际 `api.deepseek.com` / `deepseek-flash` 小请求、真实对局的完整请求与回复。官方文档说明
minimal→low、medium→high，默认 thinking enabled/high；`thinking:{type:"disabled"}` 关闭思考。

每设置 3 次同一小型资金题（2000 输出上限），不是 7 万 token 游戏观察的速度基准：

| 设置 | 延迟 p50 | 正确选择 | 有效 JSON |
|---|---:|---:|---:|
| 默认 | 7.640 s | 3/3 | 3/3 |
| minimal | 3.395 s | 3/3 | 3/3 |
| low | 4.629 s | 3/3 | 3/3 |
| medium | 10.713 s | 2/3 | 2/3 |
| high | 4.914 s | 3/3 | 3/3 |
| thinking disabled | 1.458 s | 0/3 | 3/3 |

low 中位延迟下降 39.4%；禁用思考下降 80.9%，但三次都没有最大化可买的有效单位数。
medium 一次用满 2000 token 后空回复。映射相同的参数仍因采样／网络产生波动；这不是显著性结论。
因此只能说“少思考可能帮助速度”，不能说“已经能跟上同盟对局”，也不能据此设为默认。

### 37.3 Bounded LLM rate-limit retries (round54 cycle 5)

维护者要求先处理 cycle4b 遇到的 429，再在同一代码完成 OpenCode Go Flash 默认／low A/B。
`httpDecision` 的非 200 错误只附加数字 HTTP `status` 与解析后的 `retryAfterMs`，不读取或保留
错误正文、原始头、URL 或凭据。日期与秒数格式来源为
[RFC 9110 §10.2.3](https://www.rfc-editor.org/rfc/rfc9110.html#name-retry-after)。

[ASSUMED] 仅 429／503 重试，每决策最多三次（与已有 length 追问共用计数）。等待默认 10 秒，
有效 Retry-After 上限 30 秒；等待后必须还留有原 `SP_LLM_TIMEOUT_MS` 一半的完整尝试预算，
与已有 length 重试的半预算门槛一致，醒来后再次检查。首次请求仍可用原时限；所有尝试共用
原始截止时间。调试 `rate-limit` 记 status／拟等待 waitMs／retry／attempt，不记录远端文字。
拒绝或耗尽后仍抛出通用 `LLM request`，沿用主机回退；其他状态不重试。

未修改提示、模型／强度默认、游戏数据、bot、主机时限或发布门禁。测试使用本机动态端口模拟
429→200、503、等待默认／上限／日期／无效头、三次上限、预算不足、晚醒及 length 追问共用上限。
初次定向验证：`tests 36 / pass 36 / fail 0 / skipped 0`。完整 A/B 记录随后补入。
